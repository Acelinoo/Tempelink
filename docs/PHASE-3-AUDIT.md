# TEMPELINK — PHASE 3 AUDIT REPORT
**Download Delivery & Reliability Architecture Audit**
**Date:** September 2026
**Baseline:** Phase 2.5 Live Verified Baseline (67/67 Unit Tests Passing, Next.js 16 Production Build Clean, Live RapidAPI TikTok Verified)

---

## 1. Executive Summary

Phase 2.5 proved that Tempelink can successfully resolve real-world TikTok media from an external RapidAPI provider and issue cryptographically signed download tokens. 

The objective of Phase 3 is to elevate **Download Delivery & Reliability**: ensuring that media delivery is predictable, resilient against upstream link degradation, protected against header injection, fortified with deterministic filename sanitization, safeguarded against duplicate clicks, and strictly bounded by SSRF and rate-limiting perimeter defenses without introducing bloated infrastructure (no Redis, BullMQ, FFmpeg, or databases).

## 2. Current Flow Analysis

### 2.1. Resolve Flow (`POST /api/media/resolve`)

```
        │

        │

[ TikTok Provider (Upstream query to /index, timeout 15000ms, maxRetries 2) ]
        │
        ▼

        │
        ▼
[ HMAC-SHA256 Download Token Generation (Embedded target URL + 900s expiry) ]
        │
        ▼
[ JSON Response with Normalized Metadata + Capabilities ]
```

### 2.2. Download Flows (`/api/media/download`)

Tempelink supports two coordinated download delivery mechanisms:

#### Flow A: Client API Descriptor (`POST /api/media/download`)
1. Client submits `{ mediaId, capabilityId, sourceUrl, downloadToken }`.
2. Rate limit checked (10 req/min).
3. `sourceUrl` re-checked for SSRF safety.
4. HMAC token signature verified using `crypto.timingSafeEqual()`.
5. Expiry verified against `Date.now() > payload.expiresAt`.
6. `targetUrl` extracted from token and re-verified against SSRF perimeter.
7. Telemetry event `download_started` emitted.
8. Returns JSON descriptor `{ downloadType: 'direct_url', downloadUrl, filename, mimeType, expiresAt }`.

#### Flow B: Direct Browser Stream Redirect (`GET /api/media/download?token=...`)
1. Client requests endpoint with `?token=...`.
2. Rate limit checked (10 req/min).
3. Token decoded, HMAC signature verified, expiry checked.
4. `targetUrl` validated for SSRF safety.
5. Returns HTTP `302 Found` with `Location: [targetUrl]` and `Content-Disposition: attachment; filename="[filename]"`.

## 3. Detailed Component Audit

### 3.1. Token Lifecycle & Security (`src/lib/security/token.ts`)
- **Generation:** Uses HMAC-SHA256 with `DOWNLOAD_SIGNING_SECRET`. Serializes payload as Base64URL and appends `.signature`.
- **Payload Schema:** `{ mediaId, capabilityId, sourceUrl, targetUrl, filename, mimeType, expiresAt }`.
- **Signature Verification:** Recomputes HMAC over the Base64URL payload and performs constant-time comparison via `crypto.timingSafeEqual()`.
- **Expiration:** Tokens are valid for 15 minutes (`DOWNLOAD_TOKEN_EXPIRY_SECONDS = 900`).
- **Fail-Closed Hardening:** In production (`NODE_ENV === 'production'`), if `DOWNLOAD_SIGNING_SECRET` is missing, short (< 32 chars), or matches the dev default, token signing throws `INTERNAL_ERROR`.
- **Current Limitation / Audit Finding:** Payload fields are not individually validated after `JSON.parse(payloadBase64)`. If an attacker constructs a malformed JSON payload that passes parsing (e.g. `targetUrl` is a number or missing), subsequent URL operations could throw uncaught runtime errors. **Strict payload schema validation is required.**

### 3.2. Media URL Lifecycle & Upstream URLs
- TikTok CDN URLs (e.g. `https://v16m.tiktokcdn-us.com/...`) generated by the upstream provider have ephemeral expiration parameters (`x-expires=...`, `x-signature=...`).
- **Audit Finding:** If a user waits several hours after resolving or if upstream CDN tokens expire before the Tempelink token does, redirecting the browser directly to an expired CDN link results in a raw CDN 403 Forbidden error page.
- **Remediation:** Implement lightweight upstream reachability probing (HTTP `HEAD` or `Range: bytes=0-0` with short 2s timeout) before redirecting, catching dead upstream links and converting them to user-friendly `MEDIA_URL_EXPIRED` (HTTP 410) errors.

### 3.3. Redirect Behavior & Security
- The redirect route `GET /api/media/download?token=...` issues an HTTP `302 Found`.
- **Security Check:** The destination is decoded strictly from the server-signed token. Clients cannot pass arbitrary URLs as query parameters (`?url=...` is ignored).
- **Audit Finding:** The redirect response currently lacks cache prevention headers (`Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache`, `Expires: 0`). Intermediate proxies or aggressive browser caches might cache the temporary 302 redirect.

### 3.4. HTTP Response Headers & Filename Sanitization
- `Content-Disposition` header currently formats filename as:
  ```http
  Content-Disposition: attachment; filename="${payload.filename}"
  ```
- **Audit Finding / Security Risk:** If `payload.filename` contains carriage return or line feed characters (`\r\n`), a CRLF injection attack could allow response header splitting. Furthermore, special characters (`/`, `\`, `"`, `*`, `?`, `<`, `>`, `|`, null bytes) could lead to path traversal or filesystem errors on client operating systems.
- **Remediation:** Introduce a deterministic filename sanitization utility (`sanitizeDownloadFilename`) enforcing:
  - Removal of CRLF characters (`\r`, `\n`).
  - Removal of directory traversal sequences (`..`, `/`, `\`).
  - Replacement of illegal characters with safe underscores.
  - Length capping (e.g., maximum 80 characters before extension).
  - RFC 5987 / RFC 6266 compliance (`filename="..."` and `filename*=UTF-8''...`).

### 3.5. Media Type Validation
- The current implementation assigns MIME types statically based on format (`video/mp4`, `audio/mpeg`, `image/jpeg`).
- **Audit Finding:** If the upstream provider encounters an anti-bot wall and returns an HTML error page with HTTP 200, Tempelink could inadvertently serve an HTML document disguised as an MP4 attachment.
- **Remediation:** Verify upstream `Content-Type` headers during delivery or probing, rejecting `text/html` or non-media content types.

### 3.6. Timeout & Resilience
- TikTok provider resolution uses `serverConfig.tiktok.resolveTimeoutMs` (15,000ms default) with bounded exponential backoff retries (`serverConfig.tiktok.maxRetries = 2`).
- 4xx client errors are never retried.
- Bounded timeout ensures no long-lived dangling sockets in serverless runtimes.

### 3.7. Rate Limiting (`src/lib/rate-limit/rate-limiter.ts`)
- In-memory sliding window store tracking IP hits.
- Limits: 20 req/min for resolve, 10 req/min for download.
- Returns standard rate limit headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
- Returns structured HTTP 429 `RATE_LIMITED` when exceeded.
- Limitation: In-memory store does not synchronize across distributed multi-region serverless instances (accepted Phase 3 baseline; documented for Redis migration in Phase 4+).

### 3.8. Client UX & Duplicate Click Prevention
- `CapabilitySelector` has an initial `downloadState` machine (`idle`, `downloading`, `success`, `error`).
- **Audit Finding:** While the button is disabled during `downloadState === 'downloading'`, rapid double-clicks within milliseconds before React state updates could initiate duplicate requests.
- **Remediation:** Add a debounce/in-flight ref lock in `HomePage` and `CapabilitySelector` to guarantee that concurrent duplicate clicks are blocked synchronously.

## 4. Summary of Identified Risks & Action Items

| Area | Current Risk / Limitation | Phase 3 Remediation |
| :--- | :--- | :--- |
| **Token Payload Validation** | `verifyDownloadToken` parses JSON without strict schema validation | Add strict schema checks for required fields, types, and URL format |
| **Filename Security** | Possible CRLF injection or path traversal in `filename` | Implement `sanitizeDownloadFilename` utility with RFC 5987 headers |
| **Redirect Caching** | Direct 302 redirect lacks anti-caching headers | Add `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache` |
| **Upstream Link Expiration** | Client may be redirected to expired CDN link | Add lightweight upstream check to convert CDN errors into `MEDIA_URL_EXPIRED` |
| **Media Type Spoofing** | Risk of HTML error pages served as MP4 | Enforce upstream `Content-Type` validation |
| **Duplicate Clicks** | Rapid double-clicks could trigger concurrent downloads | Implement synchronous client interaction lock |
| **Testing** | Lack of tests for filename sanitization, header injection, and payload schema | Add comprehensive test suite `tests/filename.test.ts` and expand download tests |
